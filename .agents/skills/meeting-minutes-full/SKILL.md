# 議事録整理＋ドキュメント一括整理スキル

## 概要

ユーザーが会議の議事録テキスト（書き起こし・メモ等）を貼り付けて整理を依頼したときに、以下の一連の処理を実行する：

1. 議事録の構造化・マークダウン保存（参照ドキュメントによる固有名詞補正を含む）
2. 既存ファイル（TODO.md / REVIEW_ITEMS.md / COMPLETED.md）の読み取り
3. 参照7MD（PROJECT_OVERVIEW.md / SITE_STRUCTURE.md / DESIGN_GUIDELINES.md / CONTENT_GUIDELINES.md / FIREBASE_ARCHITECTURE.md / ADMIN_REQUIREMENTS.md / ROADMAP.md）の読み取り
4. 議事録 × 既存MD の突合分析
5. 整理方針の提案・承認確認
6. 承認後のマークダウン一括整理（TODO.md / COMPLETED.md / REVIEW_ITEMS.md / 参照7MD）

## 手順

### ステップ1: 会議日付の確認

- ユーザーが会議日付を明示している場合はその日付を使用する
- 明示がない場合は、ユーザーに確認する

### ステップ2: 並列で3つの処理を同時実行

以下の3つの処理を **並列** で実行する。ただし A（議事録マークダウンの作成）は C（参照ドキュメント読み取り）の結果に依存するため、A は B・C の読み取り完了後に実行する。

#### A. 議事録マークダウンの作成・保存

貼り付けられたテキストを以下の構成でマークダウンに整理し、保存する。

**固有名詞の補正**: AI文字起こしによる議事録テキストには、団体名・ゲーム名・関係者名の表記揺れや誤変換が含まれることがある。保存前に **C で読み取った参照ドキュメントの正規表記** と照合し、誤った表記を正規表記に補正してから保存する。判断に迷う場合は元の表記を残し、ステップ4の「確認事項」に挙げる。

主な補正対象:
- 団体名: `Molkkynist`（モルキニスト）
- ゲーム名: `モルック` / `molkky`
- 関係者名: `石井さん` 等（既存MDの表記に揃える）

- ディレクトリ: `/Users/kanekohiroki/Desktop/molkkynist/meeting_notes/`
- ファイル名: `YYYY-MM-DD.md`（同日に複数の会議がある場合は `YYYY-MM-DD_2.md`）
- ディレクトリが存在しなければ作成する

```markdown
# 会議議事録 - YYYY年MM月DD日

## 参加者
- （判明している場合のみ記載、不明なら「（記録なし）」）

---

## 議題N: （議題タイトル）

### 課題
（議題の背景・課題を簡潔に記載）

### 検討内容
（議論された内容・選択肢を記載）

### 決定事項 / 設計方針
（決定された方針があれば記載）

---

（議題ごとに繰り返し）

## アクションアイテム
- [ ] （会議で決まったアクションを箇条書き）

---

## TODO追記項目（→ TODO.md）

*整理方針の承認後に反映。ここでは候補一覧のみ記載。*

| ID | 優先度 | 対象 | 内容 | 状態 |
|----|--------|------|------|------|
| （候補） | （優先度） | （対象） | （内容） | `[ ] 未着手` |

---

## 要検討事項追記項目（→ REVIEW_ITEMS.md）

*整理方針の承認後に反映。ここでは候補一覧のみ記載。*

### 決定済み → 削除対象

| ID | 決定内容 |
|----|----------|
| （候補） | （決定内容） |

### 新規追加候補

| ID | 優先度 | カテゴリ | 内容 | 状態 |
|----|--------|----------|------|------|
| （候補） | （優先度） | （カテゴリ） | （内容） | `[ ] 未着手` |
```

#### B. 既存ファイルの読み取り

以下のファイルを読み取り、既存のID・内容・状態を把握する：

1. `TODO.md` — セクションA〜Fの最新IDと全項目の内容・状態
2. `COMPLETED.md` — 既使用ID（**IDの再利用禁止のため、ここも必ず確認**）
3. `REVIEW_ITEMS.md` — 最新のR-番号と全項目の内容・状態・決定事項

#### C. 参照ドキュメントの読み取り（後続ステップで更新候補にもなる）

議事録テキストの固有名詞補正、および突合分析の文脈把握のために以下を読み取る：

- `PROJECT_OVERVIEW.md` — プロジェクト方針・目的・ターゲット・コンセプト
- `SITE_STRUCTURE.md` — ページ構成・画面設計・ナビゲーション
- `DESIGN_GUIDELINES.md` — 配色・画像素材・Image Gen 2・フォント・レイアウト
- `CONTENT_GUIDELINES.md` — 文章・コピー・告知文・活動レポート文・Instagram誘導文
- `FIREBASE_ARCHITECTURE.md` — Firebase・Firestore・Auth・Storage・Hosting・権限
- `ADMIN_REQUIREMENTS.md` — 管理画面・石井さん専用ログイン・各種編集機能
- `ROADMAP.md` — 開発順序・実装フェーズ・今後の進め方

これらは以下の用途に使用する：
1. ステップ2のAでの議事録作成時：固有名詞・表記の正規化
2. ステップ3の突合分析時：議論された内容の文脈理解
3. ステップ4の方針提案時：既存方針との整合性確認
4. ステップ6での更新対象（決定事項を該当MDに反映）

### ステップ3: 突合分析

ステップ2のA（議事録の決定事項）・B（ローカルMD）を、C（参照7MDの既存方針）と照らし合わせ、以下を分類する：

#### REVIEW_ITEMS関連

- **削除対象**: 会議で結論が出た項目（決定内容は該当する参照7MDに反映するため、REVIEW_ITEMS.mdからは削除）
- **優先度変更**: 会議の議論で優先度が変わった項目
- **新規追加候補**: 会議で新たに出た未決定の検討事項（IDはR-の連番で付与）

#### TODO関連

- **廃止候補**: 会議の決定により方針転換した既存TODO（COMPLETED.mdへ移動し、備考に「**廃止**: 理由」を記載）
- **完了候補**: 会議の決定により完了とみなせる既存TODO（COMPLETED.mdへ移動）
- **新規追加候補**: 会議で「やる」と決まった実装タスク。以下のセクション分類に従う：
  - コンテンツ追加（記事・イベントレポート等） → セクション A
  - バグ修正 → セクション B
  - UI/UX改善 → セクション C
  - 新機能（フォーム・管理画面・Firebase連携等） → セクション D
  - SEO / パフォーマンス → セクション E
  - その他 → セクション F
- **REVIEW_ITEMSからのTODO化**: 決定事項が確定し実装が必要になった元REVIEW_ITEMS項目

> **由来の自動付与**: 本スキルが追加するTODOは、すべて備考欄に `由来: 会議` を自動的に含める（追加日とあわせて記載。例: `2026-05-20 追加 / 由来: 会議`）。TODO.md のルールに準拠。

#### 参照7MD関連

- **反映対象**: 決定済み事項のうち、各参照MDに反映すべき内容の一覧
  - プロジェクト全体方針・ターゲット・コンセプト → `PROJECT_OVERVIEW.md`
  - ページ追加・削除・画面設計・ナビゲーション → `SITE_STRUCTURE.md`（**実装済みのもののみ記載**）
  - 配色・画像素材・フォント・レイアウト → `DESIGN_GUIDELINES.md`
  - 文章・コピー・告知文・誘導文 → `CONTENT_GUIDELINES.md`
  - Firebase・Firestore・Auth・Storage・権限 → `FIREBASE_ARCHITECTURE.md`
  - 管理画面・石井さん専用ログイン・編集機能 → `ADMIN_REQUIREMENTS.md`
  - 開発順序・フェーズ・今後の進め方 → `ROADMAP.md`

#### 分類の判定基準

**TODO vs REVIEW_ITEMS の判定:**
- 「やる」と決まったもの → TODO
- まだ方針が決まっていないもの → REVIEW_ITEMS

**優先度の判定:**
- 最高: サイト運営の根幹に関わり、即座に決定・実装が必要
- 高: 次の公開・運用判断までに決定・実装が必要
- 中: 将来的に必要だが急ぎではない
- 低（長期）: 長期的な検討事項

### ステップ4: 整理方針の提案 + 承認確認

ステップ3の分析結果を以下の構成でユーザーに提示する：

```
## REVIEW_ITEMS.md の修正方針

### 決定済み → 削除対象（N件）
| ID | 決定内容 | 反映先MD |

### 優先度変更（N件）
| ID | 変更前 | 変更後 | 理由 |

### 新規追加候補（N件）
| ID | 優先度 | カテゴリ | 内容 |

## TODO.md / COMPLETED.md の修正方針

### 廃止候補（→ COMPLETED.md）（N件）
| ID | 理由 |

### 完了候補（→ COMPLETED.md）（N件）
| ID | 完了根拠 |

### 新規追加候補（N件）
| ID | 優先度 | セクション | 内容 |

## 参照7MDの反映内容
- PROJECT_OVERVIEW.md: （変更箇所）
- SITE_STRUCTURE.md: （変更箇所）
- DESIGN_GUIDELINES.md: （変更箇所）
- CONTENT_GUIDELINES.md: （変更箇所）
- FIREBASE_ARCHITECTURE.md: （変更箇所）
- ADMIN_REQUIREMENTS.md: （変更箇所）
- ROADMAP.md: （変更箇所）
（変更不要のMDは「変更不要」と記載）

## 確認事項
- （判断が分かれる点、ユーザーの意図確認が必要な点）
```

最後に以下の質問を行う：

**「この方針で整理してもよろしいですか？」**

### ステップ5: ユーザーの回答に応じた分岐

| ユーザーの回答 | 処理 |
|----------------|------|
| **「はい」等のゴーサイン** | → ステップ6へ進む |
| **修正指示あり** | → 指示内容を反映してステップ4に戻り、修正版の方針を再提案する |

### ステップ6: マークダウンの一括整理（ファイル反映）

承認された方針に基づき、以下のファイルを更新する：

#### 1. REVIEW_ITEMS.md の更新
- 決定済み項目を削除する（決定内容は該当する参照7MDに反映済みであることが前提）
- 優先度が変更された項目を修正する
- 新規項目を追記する（IDはR-の連番で付与、既存項目との重複は追加しない）

#### 2. TODO.md / COMPLETED.md の更新
- 廃止項目: TODO.mdから削除し、COMPLETED.mdの該当日付セクション（`## YYYY-MM-DD`、降順）に移動。備考欄に「**廃止**: 理由」を記載
- 完了項目: TODO.mdから削除し、COMPLETED.mdの該当日付セクションに移動
- 新規項目: TODO.mdの適切なセクション（A〜F）に追記（IDは連番、既存項目との重複は追加しない）
- **新規TODOの備考欄には必ず `由来: 会議` を含める**（追加日と組み合わせ。例: `2026-05-20 追加 / 由来: 会議`）
- **IDの再利用は禁止**。TODO.md と COMPLETED.md の両方を確認し、既存の最大番号の次を使用する

#### 3. 参照7MDの更新
- ステップ3で分類された反映対象を、各参照MDに追記・修正する
- 判定ルールは `markdown-maintenance-rules` スキルに準拠
- **SITE_STRUCTURE.md には実装済みのページ・セクションのみを記載する**（未実装・計画中のページは記載しない）
- 変更不要なMDには手を加えない

### ステップ7: 完了報告

以下を日本語で報告する：

- 議事録の保存先ファイルパス
- REVIEW_ITEMS.md の変更サマリー（削除N件・優先度変更N件・追加N件）
- TODO.md / COMPLETED.md の変更サマリー（廃止N件・完了N件・追加N件）
- 参照7MDごとの変更箇所一覧（変更なしの場合は「変更不要」と明記）

## 対象となる依頼例

- 議事録を作成してください
- 議事録を整理してください
- 議事録をまとめてください
- 会議メモを整理して
- ミーティングメモをまとめて
- この会議の内容を整理して
- 会議録を整理して

## 注意事項

- 会話の書き起こしは口語的で冗長な場合が多い。重要な論点・決定事項・アクションアイテムを抽出し、簡潔に構造化する。
- 雑談・脱線部分は議事録に含めない。ただし、団体運営・ビジネス方針・サイト構成に関わる議論は雑談に見えても記録する。
- 人名の敬称は「氏」で統一する。ただし既存MD（例: `ADMIN_REQUIREMENTS.md` の「石井さん」）で別表記が確立している場合はその表記に従う。議事録内の引用部分も既存表記を尊重する。
- TODO.md / REVIEW_ITEMS.md のフォーマット・ルールは各ファイル冒頭のルールセクションに従う。
- 議事録テキストの固有名詞補正は、参照7MDに正規表記が明記されている場合のみ実施する。曖昧な場合は元の表記を保持し、ステップ4の「確認事項」でユーザーに確認する（誤った補正で議論内容を歪めないため）。
- **ステップ6（ファイル反映）はステップ5でユーザーの承認を得てから実行すること。承認なしにファイルを変更してはならない。**
- ステップ4の提案に対してユーザーから修正指示があった場合は、修正を反映して再提案する。承認されるまでステップ6には進まない。
- 追記するTODO/REVIEW_ITEMSが0件の場合は、該当セクションに「該当なし」と記載する。
- 既存のTODO/REVIEW_ITEMSと重複する内容は追加しない。関連がある場合はIDを参照する形で記載する。
- **IDの再利用は絶対禁止**。TODO.md と COMPLETED.md の両方を確認し、既存の最大番号の次を採番する。
- 参照7MDの更新判定は `markdown-maintenance-rules` の判定ルールに従う。変更が不要な場合は手を加えず、報告時に「変更不要」と明記する。
- スプレッドシート同期は現状なし。将来Firebase/Sheets連携が整備された際に本スキルに同期ステップを追記する。
