# Local Member Create

## 概要

Molkkynist の運営メンバー情報は、Firestore ではなくローカルデータと `assets/` 配下の画像で管理する。

このスキルは、ユーザーが新しいメンバー作成を依頼したときに、Markdown資料を原本として必要な入力項目を読み取り、すべての必須項目が揃ってから `js/member-data.js` への追加作業へ進むために使用する。

## 手順

### 1. Markdown原本と現行データ構造を確認する

最初に以下を確認する。

- `ADMIN_REQUIREMENTS.md`
- `FIREBASE_ARCHITECTURE.md`
- `SITE_STRUCTURE.md`
- `DESIGN_GUIDELINES.md`
- `js/member-data.js`

確認の優先順位:

- 入力時にユーザーへ提示する項目は、`ADMIN_REQUIREMENTS.md` の「メンバー管理要件（廃止）」にある「入力項目」を原本にする。
- 実装フィールドへの対応は、`FIREBASE_ARCHITECTURE.md` の `members（廃止）` と `js/member-data.js` の現在の構造で確認する。
- 表示場所、文体、画像パスの扱いは `SITE_STRUCTURE.md`、`DESIGN_GUIDELINES.md`、既存メンバーデータに合わせる。

`ADMIN_REQUIREMENTS.md` と実装フィールドがずれている場合は、Markdownの入力項目名をユーザー向けの提示名として優先し、実装時に対応する `js/member-data.js` のキーへ変換する。項目の追加・削除が必要に見える場合は、勝手にスキーマを拡張せず、ユーザーに確認する。

### 2. 入力項目を抽出して必須・任意を判断する

スキル内の固定リストを正本にしない。毎回、Markdown原本から新規メンバー追加時に提示する項目を抽出する。

判断ルール:

- `ADMIN_REQUIREMENTS.md` の「入力項目」にある項目を、原則として確認対象にする。
- URL用IDなど、公開ページ生成や `js/member-data.js` への登録に必要だがユーザーが判断しなくてよい内部項目は、実装側で自動決定する。
- 写真・画像は、原本が必須と明記していない限り、未準備なら空欄で仮登録できることを伝える。
- `FIREBASE_ARCHITECTURE.md` や `js/member-data.js` にだけ存在する表示補助項目は、ユーザーへ提示する必要があるかを原本と表示要件から判断する。

ユーザーに入力してもらう項目:

- 名前
- 役割
- 職業
- 写真を使うかどうか、使う場合の画像
- モルックを始めたきっかけ
- モルック以外の好きなこと
- 初参加者へのメッセージ
- ひとことコメント

実装側で自動決定する項目:

- URL用ID: 既存IDと重複しない小文字英数字・ハイフンの値を生成する。
- ビジュアル種別: 画像なし時の表示バランスを見て、既存の `visualVariant` に合わせて選ぶ。
- 表示順: 既存メンバーの最大表示順の次になる値を自動採番する。
- 公開状態: 明示的に非公開指定がない限り `true` にする。
- 画像パス: 画像がない場合は空欄、画像がある場合は `assets/images/members/` 配下のパスへ変換する。

`ADMIN_REQUIREMENTS.md` に「表示順」「公開状態」が含まれていても、通常はユーザーに質問せず上記ルールで自動決定する。ただし、ユーザーが並び順や公開状態を明示した場合は、その指定を優先する。

### 3. 未入力項目を質問する

ユーザーの初回依頼に含まれている項目は再質問しない。

未入力項目がある場合は、一度に3項目程度まで質問する。回答を受け取ったら、埋まった項目を保持し、残りの未入力項目だけを追加で質問する。

質問は、すべての必須項目が埋まるまで続ける。

画像が未準備の場合は、`image` を空欄にしてプレースホルダー表示で仮登録できることを伝える。写真を使う場合は、画像を `assets/images/members/` 配下へ置く方針でファイル名を確認する。

### 4. 入力内容を正規化する

- URL用IDは小文字英数字とハイフンを基本にする。
- 表示順は数値にする。
- 公開状態は true / false にする。
- 文体は既存メンバーと揃え、過度に長い紹介文にしない。
- Markdown原本の項目名と `js/member-data.js` のキーが異なる場合は、対応関係を明確にしてから変換する。

### 5. 追加前に確認する

すべての必須項目が揃ったら、`js/member-data.js` へ追加する前に確認用の要約を提示する。

確認する内容は、Markdown原本から抽出したユーザー入力項目と、実装側で自動決定した項目を分けて提示する。スキル内の固定リストだけで要約せず、必ずMarkdown原本と現行データ構造を照合する。

ユーザーが修正を希望した場合は、該当項目だけを聞き直す。

### 6. ローカルデータへ追加する

確認が取れたら、`js/member-data.js` の `MEMBER_ITEMS` に新しいメンバーを追加する。

画像ファイルが提供されている場合は、プロジェクト内の既存方針に従って `assets/images/members/` 配下へ配置する。画像ファイルが未提供の場合は `image: ""` とし、プレースホルダー表示にする。

### 7. 検証する

変更後は以下を確認する。

- `node --check js/member-data.js`
- `node --check js/member-list.js`
- `node --check js/member-detail.js`
- トップページ `#members` で表示されること
- `member.html?id=<id>` で詳細表示されること

## 対象となる依頼例

- メンバーを作成したい
- メンバーを追加したい
- 新しい運営メンバーを登録したい
- メンバー紹介を1人増やしたい
- ローカルデータにメンバーを追加して

## 注意事項

- メンバー情報は Firestore に保存しない。
- 管理画面 `admin/members.html` は使わない。
- 画像URLの手入力運用には戻さない。
- 個人情報寄りの項目（年齢、住所、連絡先、個人SNSなど）は追加しない。
- 新規追加時に提示する項目は、スキル本文ではなくMarkdown原本を正本にする。
- ユーザーがすべての必須項目を埋めるまで、実データ追加へ進まない。
- `.claude/skills/local-member-create/SKILL.md` と `.agents/skills/local-member-create/SKILL.md` は同一内容を維持する。
